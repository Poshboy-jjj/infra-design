### 3.2 サイジング根拠
本システム（k8sクラスタ）に割り当てるリソースの選定根拠を以下に示す。

* **vCPU / vRAM 算出根拠**:
  * **コントロールノード**:
    * **役割**: etcd、kube-apiserver、kube-scheduler 等の制御コンポーネントの安定運用。
    * **選定根拠**: Kubernetes公式の推奨最小スペック（2 vCPU / 4 GB RAM）を採用。コントロールプレーン単体動作のため過度なリソースは割り当てず、軽量構成とする。
  * **ワーカーノード（2台）**:
    * **想定負荷・Pod規模**: 自作Webアプリ（フロント/API）、ブログ用Web/AP Pod（WordPress/Ghost等）、cert-manager、Ingress-nginx、統合監視（Exporter）等の複数Pod実行を想定。（※データベースは別VMに分離）
    * **推奨スペック**: アプリケーションPod群の消費メモリ（約 2〜3 GB）に対し、OS・kubelet用リソース（約 1.5 GB）および将来的な追加Pod用バッファ（2 GB）を加味し、1台あたり 4 vCPU / 8 GB RAM と算定。
    * **ノード分散**: ワーカー2台構成とすることで、片系メンテナンス時やノード障害時にも重要Podを再配置・即時縮退運転できる可用性を確保。

* **ディスク容量（vDisk）算出根拠**:
  * **コントロールノード（40 GB）**:
    * **OS・コンテナランタイム領域**: 20 GB（AlmaLinux基本機能 ＋ containerd）
    * **etcd / ログ・証明書領域**: 20 GB（etcdデータベース、k8s制御ログ、監査ログ）
  * **ワーカーノード（80 GB / 台）**:
    * **OS・ミドルウェア領域**: 20 GB（固定）
    * **コンテナイメージキャッシュ・Podローカル領域**: 30 GB（ビルド・デプロイ時のイメージ保持）
    * **ログ・一時データ領域**: 20 GB（Podログ、/var/log/pods、コンテナローテーション用）
    * **安全バッファ**: 10 GB（安全率 約1.15〜1.25倍を考慮）

## 6. 機能要件に対する設計

### 6.1 Kubernetesクラスタ設計
本サーバで構築するKubernetesクラスタの基本設計方針を以下に定義する。

#### 6.1.1 アーキテクチャ・基本仕様
* **ノード構成**: コントロールプレーン1台、ワーカーノード2台の構成とし、コントロールプレーンは制御専用、ワーカーノードはワークロード実行専用とする。
* **基本コンポーネント**: Kubernetes（kubeadm構成）、コンテナランタイム（containerd）。

#### 6.1.2 クラスタネットワーク設計（CNI / Service）
* **CNIプラグイン**: Calico（Node間のPodオーバーレイ通信、ネットワークポリシー制御）
* **IPアドレス設計**: Pod CIDR（`10.244.0.0/16`）、Service CIDR（`10.96.0.0/12`）

#### 6.1.3 外部公開・ロードバランサ設計（Ingress / L4 LB）
* **L4 ロードバランサ（MetalLB）**: L2モード動作とし、VIPアドレスプール（`10.x.x.200-210`）から外部公開用IPを割り当てる。
* **Ingress Controller**: ingress-nginx を使用し、外部からのHTTPS通信を単一窓口で受けて各Serviceへルーティングする。

#### 6.1.4 ワークロード・リソース設計
役割およびセキュリティレベルの異なるコンポーネントをNamespace単位で分離し、各ワークロードのリソース割当および冗長化方針を以下のように定義する。

| Namespace | ワークロード名 | Kind | レプリカ数 | CPU Request / Limit | RAM Request / Limit | 備考・用途 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `kube-system` | `coredns` / `kube-proxy` | Deployment / DaemonSet | - | - / - | - / - | k8s標準コンポーネント |
| `ingress-nginx` | `ingress-nginx-controller` | DaemonSet | - | 100m / 500m | 128Mi / 512Mi | 外部トラフィック受入・ルーティング |
| `cert-manager` | `cert-manager` | Deployment | 1 | 50m / 100m | 64Mi / 128Mi | TLS証明書自動更新 |
| `monitoring` | `node-exporter` | DaemonSet | - | 50m / 100m | 64Mi / 128Mi | 全ノードメトリクス収集 |
| `prod-app` | `wordpress` | Deployment | 2 | 250m / 500m | 512Mi / 1Gi | Web/AP本体（本番用冗長構成） |
| `prod-app` | `my-api-service` | Deployment | 2 | 200m / 400m | 256Mi / 512Mi | 自作APIサービス（本番用冗長構成） |
| `dev-app` | テスト用Pod群 | Deployment | 1 | 100m / 200m | 128Mi / 256Mi | 開発・検証用環境 |

#### 6.1.5 永続ストレージ設計（CSI / StorageClass）
* **デフォルト StorageClass**: `local-path-provisioner`（ワーカーノードローカルディスク `/var/openebs` の活用）
* **ステートフル・データ方針**: データベース（PostgreSQL/MySQL等）は本クラスタ外の「独立DB VM」へ外だし構成とし、k8s側は原則ステートレスなWeb/AP層に特化する。

#### 6.1.6 運用アドオン・外部連携設計
* **内部DNS**: CoreDNS
* **証明書管理**: cert-manager（Let's Encrypt連携による証明書自動発行・更新）
* **外部DB接続**: Pod内にDB接続情報（ユーザー名・パスワード・接続先ホスト）を直接保持せず、`Secret` / `ConfigMap` 経由で安全に注入する。

## 7. 非機能要件に対する設計### 7.1 可用性設計
本システムにおける主要コンポーネントの障害モード、サービス・運用への影響、および可用性対策（単一障害点の排除・自動復旧方針）を以下に定義する。

| 対象コンポーネント | 障害モード / 発生事象 | サービス・運用への影響 | 可用性対策・復旧方針 |
| :--- | :--- | :--- | :--- |
| **k8s コントロールノード** (`master01`) | OS停止 / 物理サーバ・ハイパーバイザ障害 | k8s APIおよび管理機能（Pod配置・更新・スケール等）が停止。**既存のPod・Web/APサービス自体は影響を受けず稼働を継続**する。 | 制御機能のみの一時停止（縮退動作）を許容する単一構成。ESXi等の仮想基盤HA機能による自動再起動、またはバックアップ（etcd等）からのリビルドにより復旧する。 |
| **k8s ワーカーノード** (`worker01` / `worker02`) | 1台のOS停止 / ネットワーク不通 | 該当ノード上のPodが停止し、一時的にクラスタ全体の処理能力が低下する。 | **2台による冗長構成**。NodeLease/Kubelet検知により、障害ノード上のPodは正常なワーカーノードへ**自動的に再配置・再起動**（Self-healing）され、サービスを即時縮退継続する。 |
| **アプリケーションPod** (`wordpress` / `my-api`) | プロセスフリーズ / メモリ枯渇 (OOM) | 該当Podへのリクエストがエラーまたはタイムアウトとなる。 | `livenessProbe` / `readinessProbe` によりk8sが不健全状態を自動検知し、**Podを自動再起動・トラフィックから即座に切り離し**を実施する。 |
| **アプリケーションPod** (Pod全体) | 複数Pod中の1台が停止 | 単一Podの処理能力分だけリクエスト処理能力が低下する。 | `Deployment` により**レプリカ数2以上**で常時稼働。Ingress/Serviceが正常なPodのみにトラフィックをロードバランスするため、無停止でサービスを継続する。 |
| **Ingress Controller** (`ingress-nginx`) | 1ノード上のPod停止 | 該当ノード経由のVIPトラフィック処理能力が一時低下する。 | **DaemonSet 構成**により全ワーカーノードに配置。MetalLBと連携し、正常なノード上のIngress Controllerへ自動的にトラフィックを切り替える。 |
| **外部DB VM** (`db01`) | OS停止 / DBプロセスダウン | Web/APからのDB接続が不可となり、DB読み書きを伴う機能が停止する。 | 単一VM構成のため、DBプロセス監視（systemd自動再起動）および仮想基盤HAによる自動再起動で復旧を図る。（※将来的にDBレプリケーション構成へ拡張可能な設計とする） |
